cert-manager: 429 urn:ietf:params:acme:error:rateLimited: too many certificates

Let's Encrypt has stopped issuing for this name, and cert-manager is only relaying the refusal. The usual trigger is the duplicate certificate limit: five certificates for the exact same set of hostnames in seven days. You reach it by deleting the TLS Secret to 'retry', or by rebuilding a cluster or namespace repeatedly, because each rebuild orders a fresh certificate. Nothing in the cluster can clear it. The message carries a retry-after time, and retrying sooner only keeps the limit topped up.

Quick fix

Read the commands before running them. Anything that restarts a service, deletes data or changes permissions should be tried on a non-production system first.

Quick fix
# 1. Read the exact limit and the retry-after time
kubectl describe order -A | grep -B2 -A6 rateLimited
kubectl get certificaterequest -A
# 2. Stop the retries so you do not keep hitting the limit
kubectl -n apps get certificate
# 3. Count what has been issued for the name this week (public CT logs)
curl -s 'https://crt.sh/?q=app.example.com&output=json' | jq -r '.[].not_before' | sort | tail -10
# 4. A different set of names is a different bucket: adding a SAN gets you a
#    certificate now if you cannot wait
#    dnsNames: [app.example.com, www.app.example.com]
# 5. Test against staging, which has far higher limits, and switch back after
#    server: https://acme-staging-v02.api.letsencrypt.org/directory
# 6. Keep the Secret: back it up before tearing a cluster down
kubectl -n apps get secret app-tls -o yaml > app-tls.backup.yaml

How to diagnose Ingress errors

An Ingress failure is a routing failure, and there are only a few places it can break: the IngressClass is missing so no controller claims the resource, the path or host does not match, the backing Service has no endpoints, or the TLS secret is absent or in the wrong namespace. The "default backend - 404" page is the controller saying it received the request but found no rule for it.

If the quick fix above does not resolve it, work through these steps. They apply to this whole class of error, not just to this one message, which is usually what saves the time.

  1. Work backwards from the pod: kubectl get endpoints <service>. If it is empty, the Service selector does not match any ready pod and no Ingress configuration will help.
  2. Check that a controller has claimed the Ingress: kubectl describe ingress <name> should show events and an assigned address. No address means no controller is watching that IngressClass.
  3. Read the controller's own logs (kubectl logs -n ingress-nginx deploy/ingress-nginx-controller). They log rejected configuration and certificate problems explicitly.
  4. Remember TLS secrets must live in the same namespace as the Ingress. This is the single most common TLS mistake.
  5. Verify path type semantics: Prefix, Exact and ImplementationSpecific match differently, and regex behaviour varies between controllers.

Tools worth reaching for

  • kubectl describe ingress
  • kubectl get endpoints
  • controller logs
  • curl -H 'Host: …'
  • openssl s_client -servername
